# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**Wochenkorb** is a German-language, mobile-first grocery shopping list web app: shopping list, receipt scanning (real client-side OCR via Tesseract.js), purchase history, spending statistics, product/category/market management. All data is stored client-side in `localStorage` — there is no backend and no build step.

The entire application — HTML shell, CSS design system, and all JavaScript — lives in the single file `index.html` (~2150 lines; the file itself is ~210 KB because the app icon is embedded as base64 image data, see "App icon" below). This is deliberate: the same file is also published as a self-contained Claude Artifact, which does not support external JS/CSS files, `import` modules, or a build step. Any change must keep working as one file.

## Commands

There is no `package.json`, no build tool, no linter, and no automated test suite — this is intentional for a zero-dependency single-file app.

- **Run locally**: serve the directory with any static file server, e.g. `npx serve .`, then open the printed URL. Opening `index.html` directly via `file://` also works but is not representative of how it's deployed (Artifact / GitHub Pages), so prefer a real HTTP server when testing.
- **Testing**: manual, in a browser. There is no unit/e2e test runner. When verifying a change, actually load the page and click through the affected flow (the app has no error boundary beyond the try/catch in `render()`, which only prevents a white screen — it does not validate correctness). **Always check the mobile layout specifically** (resize the viewport below 900px, or use device emulation) — the desktop/mobile split is a CSS breakpoint (`@media (min-width:900px)`), not a separate build, so it's easy to silently break on mobile while only eyeballing desktop.
- **Deploy**: the file is pushed as-is to `https://github.com/CarloMeier1981/einkaufs-app` (`main` branch), which is:
  - republished as a Claude Artifact for the Claude-account use case, and
  - served live and publicly at `https://carlomeier1981.github.io/einkaufs-app/` via GitHub Pages (Settings → Pages → Deploy from branch `main` / root) for the no-Claude-account use case. The repo was made **public** specifically because free-tier GitHub Pages branch-deployment isn't available on private repos.

  There is no CI/build pipeline in between — whatever is in `index.html` on `main` is the shipped app, on both channels. **A change only intended for one channel is not possible** — always sanity-check that a change works both as a Claude Artifact (`window.claude` present) and as a bare static file (`window.claude` absent, e.g. via `npx serve`). "File download/export" below is the one place that branches deliberately on `window.claude`; "Receipt scanning" below is a second place where behavior differs between channels, but as an unavoidable side effect of the Artifact viewer's CSP rather than a deliberate branch.

## Architecture

### File layout inside `index.html`

- Lines 1–13: `<meta charset>`, **`<meta name="viewport">`**, `<title>`, the single *network* external dependency — a Google Fonts `<link>` (Orbitron + Titillium Web) — and the app-icon `<link>`/`<meta>` tags (favicon, apple-touch-icon, web manifest, theme-color; all embedded as data URIs, no network request — see "App icon" below). No other external resources are loaded; the app must keep working fully offline after first load. **Do not remove the viewport meta tag** — without it, mobile browsers lay the page out at a virtual desktop width (~980px) and zoom it down, which both breaks the `min-width:900px` sidebar breakpoint (it fires on phones too) and makes all text unreadably small. This file has no `<head>`/`<body>` wrapper of its own (the Claude Artifact publisher injects one; GitHub Pages relies on the browser's HTML parser to auto-repair it) — anything meant to end up in `<head>` must still be placed up here, before the shell markup.
- Lines 14–311: `<style>` — the entire CSS design system (see below).
- Lines ~312–326: the static app shell markup (`#app`, `.sidebar`, `.topbar`, `#view`, `.bottomnav`, `#modal-root`, `#toast-root`). This is the *only* HTML that isn't generated by JS — everything inside `#view`, `#modal-root`, `.sidebar` and `.bottomnav` is rendered at runtime.
- Lines 327–2149: one `<script>` block, organized into clearly delimited sections (search for `/* ===== Section Name ===== */`):
  - **Utilities** (~329) — `esc`/`escAttr` (HTML-escaping for interpolated user text), `fmtEUR`, `fmtDate`, `normName` (diacritic-stripping normalizer used for search/matching), date-range helpers.
  - **Constants** (~345) — `DEFAULT_CATEGORIES`, `DEFAULT_MARKETS`, `UNITS`, `CATEGORY_KEYWORDS` (keyword → category auto-classification map), `DEMO_PRODUCT_POOL` (used for demo-data seeding).
  - **Store / persistence** (~408) — the entire data model and its `localStorage` I/O. See "Data model" below.
  - **Demo data** (~481) — `seedDemoData()` / `removeDemoData()`, all demo records are tagged `isDemo:true` so they can be identified and bulk-removed.
  - **Toast & Modal** (~538) — `toast()`, `openModal()`/`closeModal()`, rendering into the static `#toast-root` / `#modal-root` containers.
  - **Router** (~553) — hash-based routing (`#/path` or `#/path/param`), see "Routing & rendering" below.
  - **Theme** (~622) — applies `data-theme` attribute to `<html>` per the stored setting.
  - **Derived data helpers** (~630) — cross-cutting queries over the store (e.g. `shoppingsInRange`, `avgPurchaseIntervalDays`, `avgPrice`) used by the dashboard and statistics views.
  - **Per-view sections** (Dashboard ~688, Einkaufsliste ~781, Scan ~917, Historie ~1015, Statistik ~1066, Produkte ~1239, Kategorien ~1308, Märkte ~1330, Suche ~1367, Einstellungen ~1393) — each contains a `viewX()` function returning an HTML string, plus any view-local state and chart-drawing functions (`svgLine`, `svgSparkline`, `drawStatistikCharts`, etc. — hand-written inline SVG, no charting library).
  - **Actions** (~1445) — every state-mutating function (add/edit/delete for products/categories/markets/list items, scan confirmation, import/export, etc.), ending in the `App = {...}` object (~2132) that re-exports them for use as `onclick="App.xxx(...)"` handlers.
  - **Boot** (~2143) — `loadStore()`, `applyTheme()`, `window.addEventListener('hashchange', render)`, initial `render()`, and the first-run demo-data onboarding modal.

### Rendering model

There is no framework/virtual DOM. `render()` (in Router) reads `location.hash`, calls the matching `viewX()` function to get an HTML string, and does `view.innerHTML = html`. Every state change is followed by `saveStore()` (persist) and `render()` (re-render the whole current view from scratch) — there is no partial/diffed update, so **any action that mutates `store` must call both**, or the UI will silently drift from persisted state.

Interactivity is wired via inline `onclick="App.methodName('id')"` attributes generated inside the template strings, not event delegation. Because of this:
- Inline handler arguments must only ever be IDs/enum values (never raw user-entered text) — anything else can break the HTML attribute on names containing quotes.
- All interpolated user-facing text (product names, notes, market names, etc.) must go through `esc()` (for HTML content) or `escAttr()` (for `value="..."` attributes) — this is how the app avoids XSS/markup breakage from a product named e.g. `Chips & "Salz"`.
- A few continuous-input fields (the receipt-scan review table) intentionally skip a full `render()` on every keystroke to avoid losing focus/cursor position — they mutate the in-memory draft object directly and patch just the total via a targeted DOM update (`updateScanTotalDisplay()`). Follow this pattern for any other free-text field inside a list/table if a full re-render would steal focus.

### Data model (`store`, `STORAGE_KEY = 'wochenkorb.store.v1'`)

Single JSON blob in `localStorage`, shape defined by `freshStore()`:

```
{ version, categories[], products[], shoppingList[], shoppings[], priceHistory[], markets[], categoryCorrections{}, settings{} }
```

- `products[]` — the catalog (name, categoryId, barcode, defaults, `favorite`, `purchaseCount`, `lastPurchasedAt`, `isDemo`).
- `shoppingList[]` — the *current, active* list (unchecked + checked-but-not-yet-completed items), each referencing a `productId`.
- `shoppings[]` — completed purchase history. Each `Shopping` embeds its own denormalized `items[]` (name/qty/price/categoryId snapshotted at purchase time) — **not** a live reference to `products[]`. This is intentional: deleting a product must not corrupt past history (see `deleteProduct()` vs. how `viewVerlaufDetail` renders items straight from the embedded snapshot).
- `priceHistory[]` — one entry per (product, shopping) purchase, used for price-trend charts and market price comparison; rebuilt/appended whenever a shopping is saved (`completePurchase`, `confirmScan`).
- `categoryCorrections{}` — a `normalizedProductName → categoryId` map. `classifyProduct()` checks this before falling back to `CATEGORY_KEYWORDS` substring matching; it's how the app "learns" from manual category corrections during receipt review.
- Deleting a category reassigns any referencing `products`/`shoppingList` items to the `Sonstiges` category (`sonstigeId()`) rather than leaving dangling references — replicate this pattern for any new entity-deletion logic.

### Receipt scanning

`Kassenzettel scannen` uses a real `<input type="file" accept="image/*" capture="environment">` (opens the phone camera on mobile) followed by canvas-based downscaling/compression (`compressImage()`, max width 1000px, JPEG q=0.72) before the image is stored inline as a data URL on the `Shopping` record.

OCR is real, via **Tesseract.js**, run entirely client-side (`runRealScan()`, ~1634) — no image is ever sent anywhere. Because this project has no build step/bundler, the library itself is **lazy-loaded from a CDN** (`loadTesseract()`, ~1620) only when a scan starts, not at page load. This has one important consequence documented in "Deploy" above: **the Claude Artifact viewer's strict CSP blocks external script/network requests**, so `loadTesseract()` will fail there (and on any fully offline device) — this is caught deliberately and surfaces as the normal `scanState.status='error'` UI with a "Manuell erfassen" fallback, rather than crashing. On GitHub Pages / `npx serve` / `file://` it works normally, downloading the German (`deu`) language model on first use (cached by the browser afterward). `Tesseract.recognize()` is called with `tessedit_pageseg_mode: '6'` ("assume a single uniform block of text") rather than the default automatic layout detection — this is more reliable for the narrow, columnar text on a photographed receipt. When touching this code, verify **both** paths: a real scan on GitHub Pages/`npx serve`, and the graceful-failure message inside a Claude Artifact (or with dev tools offline).

`parseReceiptText()` (~1660) turns Tesseract's raw recognized text into structured items with a line-based heuristic (not a general receipt parser) — this was tuned against a real photographed Kaufland receipt (not just clean synthetic text), which surfaced most of the edge cases below:
- **Market/date/total**: known market names are matched in the first few lines; a `dd.mm.yyyy`-style date anywhere in the text; a "Summe/Gesamt/Total" line (not "Zwischensumme") for the printed total.
- **Item cutoff**: only lines *before* the Summe line are considered for items — everything after (payment method, tax-rate breakdown table, Kundenbeleg footer) is guaranteed not to be a product and is ignored outright, rather than relying on `RECEIPT_NOISE` to catch every possible footer line. Since OCR sometimes garbles "Summe" itself beyond recognition (seen in testing: read as "Sunne"), there's a second, independent cutoff anchor — the payment-method line (`kartenzahlung|ec-cash|girocard`) — and whichever anchor appears first in the text wins.
- **Price extraction** (`findTrailingPrice()`, ~1705, inside `parseReceiptText`): takes the *last* valid `\d{1,4}[.,]\d{2}` number found anywhere in the line, not a strict end-of-line anchor. Real photographed receipts frequently have OCR noise/watermark artifacts trailing the actual price (e.g. a line reads as `2,79 B VA A` or `1.748 U 8` instead of `2,79 B`) — an end-anchored regex threw such lines away entirely; this cost 12 of 20 real items in testing before the fix.
- **Quantity**: recognizes both a leading `Nx` prefix (`2x Produkt`) and the "menge × Einzelpreis" format printed inline by some tills (`Produkt  2 * 0,79  1,58`, i.e. quantity/unit-price embedded before the line-total price) — the latter is stripped out of the name so it doesn't end up as name junk.
- **Negative amounts are never imported as items** — a leading `-` on the trailing price (Rabatt, Pfand-Rückgabe, Storno, e.g. `Leergut Getränke -12,02`) causes the line to be skipped. `Pfand`-labelled lines are also skipped via `RECEIPT_NOISE` regardless of sign (deposits aren't products).
- **`excludedAdjustment`**: Pfand and negative amounts are excluded from the item list, but they *are* part of the printed Summe. `parseReceiptText()` tracks their net effect in `draft.excludedAdjustment` (Pfand adds, negative amounts subtract) so `viewScanReview()` can compare the sum of imported items against `total - excludedAdjustment` instead of `total` directly — otherwise the "Preise prüfen" mismatch warning would fire on essentially every receipt that has any Pfand or discount line, even when everything was recognized correctly.

It's intentionally forgiving rather than exact — the review table is always editable before saving, since OCR/parsing mistakes are expected on real photos (a garbled price with no recoverable decimal separator, e.g. a comma OCR'd away entirely, still can't be recovered and has to be added manually).

Each parsed item is matched against the existing catalog by `normName()`; unmatched names are flagged `isNew:true` and shown with a "Neu" badge in the review table purely as a UI hint. The actual auto-creation of new products happens where it already did before this OCR change — `findOrCreateProduct()` (~469), called from `confirmScan()` for every item, creates a catalog entry if none matches by normalized name. This is generic to both scanned and manually-entered items and needs no special-casing for "new from OCR".

If the OCR engine is ever swapped again, keep it behind the same `scanState` contract (`idle → scanning → review → (confirm/cancel)` or `error`) so the rest of the flow (review/edit table, category auto-classification, `confirmScan()`) keeps working unchanged.

### App icon (favicon / apple-touch-icon / web manifest)

The app icon (a hand-authored neon shopping-basket SVG, TRON-styled to match the rest of the UI) is embedded directly in the `<link>`/`<meta>` tags at the top of the file (lines ~6–13) as **data URIs** — there is no separate `.svg`/`.png` asset file, keeping the single-file constraint intact:
- `<link rel="icon" type="image/svg+xml">` — the crisp SVG favicon for modern browsers.
- `<link rel="icon" type="image/png" sizes="32x32">` — small PNG fallback favicon.
- `<link rel="apple-touch-icon" sizes="180x180">` — shown when added to the home screen on iOS.
- `<link rel="manifest">` — an inlined (data-URI) web manifest with 192×192 and 512×512 icons, for "Add to Home Screen"/install on Android.
- `<meta name="theme-color">` and the `apple-mobile-web-app-*` meta tags, for a cleaner standalone-launch appearance.

The 180/192/512px icons are stored as **JPEG, not PNG** — the icon's background is fully opaque (no transparency needed), and JPEG compresses its glow/gradient far better than PNG (a PNG export of the same icon was ~5–10× larger). This keeps the total embedded-icon footprint to ~80 KB despite four different sizes. All of this is data URIs, so — unlike Tesseract.js — it works identically under the Claude Artifact viewer's strict CSP (no external request is made).

There's no build step to regenerate these: if the icon is ever redesigned, re-render the SVG to a `<canvas>` at each target size (`canvas.toDataURL('image/jpeg', 0.92)` for the raster sizes, keep the 32px favicon as PNG since it's tiny) and paste the resulting data URIs back into the `<link>`/manifest tags by hand.

### File download/export

`Export (JSON)`/`Export Historie (CSV)` both go through `offerDownload()` (~2044), which branches on whether a Claude runtime is present — this is the **only** place in the app that touches `window.claude`, and the only functional difference between the two deployment channels:
- **Inside the Claude Artifact viewer** (`window.claude.use` exists): uses the `downloads` runtime capability (`window.claude.use('downloads')`). A plain `<a download>` link is inert inside that sandbox, so this path is required there; it also handles `extension_not_enabled` (retries the CSV export as `.txt`) and a user `declined` response.
- **Everywhere else** (GitHub Pages, `file://`, `npx serve`, ...): falls back to `nativeDownload()` (~2033), a standard `Blob` + temporary `<a download>` click — ordinary browser download, no Claude dependency at all.

Both paths must keep working — when touching export/import, verify with `window.claude` both present (mock `window.claude.use` in the console) and absent (plain `npx serve`, the GitHub Pages case). Import (`importJson()`) has no such split — it's a plain `<input type="file">` + `FileReader`, which already works identically everywhere.

### CSS design system

All theming is CSS custom properties on `:root`, following a **dark-first** three-state pattern (the app currently ships a TRON-inspired dark HUD aesthetic as the default):
- Bare `:root` defines the dark palette (the default/system look).
- `@media (prefers-color-scheme: light)` + `:root:not([data-theme="dark"])` overrides to a light "glass" companion palette.
- `:root[data-theme="light"]` repeats the light overrides so the in-app theme toggle (Einstellungen → Hell/Dunkel/System) wins regardless of OS preference.

Effects like glow/bloom are tokenized (`--glow-sm`, `--glow-md`, `--text-glow`, `--chart-glow`) rather than hardcoded per component, specifically so the light theme can disable/soften them (a static neon text-shadow looks wrong on a white background) — when adding a new glowing element, use the tokens rather than a literal `rgba(0,229,255,...)` shadow. Category/series colors (`--cat-1`…`--cat-8`) are picked per-category via a stable hash (`catColorVar()`), not by list position, so a given category keeps the same color across renders and datasets.
