# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**Wochenkorb** is a German-language, mobile-first grocery shopping list web app: shopping list (with voice input via the Web Speech API), receipt scanning (real client-side OCR via Tesseract.js), a REWE ordering assistant that prepares the list and hands it off to rewe.de, purchase history, spending statistics, product/category/market management. All data is stored client-side in `localStorage` — there is no backend and no build step.

The entire application — HTML shell, CSS design system, and all JavaScript — lives in the single file `index.html` (~2640 lines; the file itself is ~232 KB because the app icon is embedded as base64 image data, see "App icon" below). This is deliberate: the same file is also published as a self-contained Claude Artifact, which does not support external JS/CSS files, `import` modules, or a build step. Any change must keep working as one file.

## Commands

There is no `package.json`, no build tool, no linter, and no automated test suite — this is intentional for a zero-dependency single-file app.

- **Run locally**: serve the directory with any static file server, e.g. `npx serve .`, then open the printed URL. Opening `index.html` directly via `file://` also works but is not representative of how it's deployed (Artifact / GitHub Pages), so prefer a real HTTP server when testing.
- **Testing**: manual, in a browser. There is no unit/e2e test runner. When verifying a change, actually load the page and click through the affected flow (the app has no error boundary beyond the try/catch in `render()`, which only prevents a white screen — it does not validate correctness). **Always check the mobile layout specifically** (resize the viewport below 900px, or use device emulation) — the desktop/mobile split is a CSS breakpoint (`@media (min-width:900px)`), not a separate build, so it's easy to silently break on mobile while only eyeballing desktop.
- **Deploy**: the file is pushed as-is to `https://github.com/CarloMeier1981/einkaufs-app` (`main` branch), which is:
  - republished as a Claude Artifact for the Claude-account use case, and
  - served live and publicly at `https://carlomeier1981.github.io/einkaufs-app/` via GitHub Pages (Settings → Pages → Deploy from branch `main` / root) for the no-Claude-account use case. The repo was made **public** specifically because free-tier GitHub Pages branch-deployment isn't available on private repos.

  There is no CI/build pipeline in between — whatever is in `index.html` on `main` is the shipped app, on both channels. **A change only intended for one channel is not possible** — always sanity-check that a change works both as a Claude Artifact (`window.claude` present) and as a bare static file (`window.claude` absent, e.g. via `npx serve`). "File download/export" below is the one place that branches deliberately on `window.claude`; "Receipt scanning", "Voice input" and "REWE-Bestellassistent" below are further places where behavior differs between channels, but as an unavoidable side effect of the Artifact viewer's strict CSP (blocks the Tesseract.js CDN load, in practice blocks microphone access for `SpeechRecognition`, and may block or sandbox the `window.open()` popup the REWE hand-off relies on) rather than a deliberate branch.

## Architecture

### File layout inside `index.html`

- Lines 1–13: `<meta charset>`, **`<meta name="viewport">`**, `<title>`, the single *network* external dependency — a Google Fonts `<link>` (Orbitron + Titillium Web) — and the app-icon `<link>`/`<meta>` tags (favicon, apple-touch-icon, web manifest, theme-color; all embedded as data URIs, no network request — see "App icon" below). No other external resources are loaded; the app must keep working fully offline after first load. **Do not remove the viewport meta tag** — without it, mobile browsers lay the page out at a virtual desktop width (~980px) and zoom it down, which both breaks the `min-width:900px` sidebar breakpoint (it fires on phones too) and makes all text unreadably small. This file has no `<head>`/`<body>` wrapper of its own (the Claude Artifact publisher injects one; GitHub Pages relies on the browser's HTML parser to auto-repair it) — anything meant to end up in `<head>` must still be placed up here, before the shell markup.
- Lines 14–326: `<style>` — the entire CSS design system (see below).
- Lines ~327–341: the static app shell markup (`#app`, `.sidebar`, `.topbar`, `#view`, `.bottomnav`, `#modal-root`, `#toast-root`). This is the *only* HTML that isn't generated by JS — everything inside `#view`, `#modal-root`, `.sidebar` and `.bottomnav` is rendered at runtime.
- Lines 342–2639: one `<script>` block, organized into clearly delimited sections (search for `/* ===== Section Name ===== */`):
  - **Utilities** (~344) — `esc`/`escAttr` (HTML-escaping for interpolated user text), `fmtEUR`, `fmtDate`, `normName` (diacritic-stripping normalizer used for search/matching), date-range helpers.
  - **Constants** (~360) — `DEFAULT_CATEGORIES`, `DEFAULT_MARKETS`, `UNITS`, `CATEGORY_KEYWORDS` (keyword → category auto-classification map), `VOICE_NUMBER_WORDS`/`VOICE_UNIT_WORDS` (German number-word and unit-synonym maps used by the voice-input parser, see "Voice input" below), `DEMO_PRODUCT_POOL` (used for demo-data seeding), `REWE_SHOP_URL`/`REWE_MARKET_SEARCH_URL`/`REWE_ALLOWED_HOSTS` (fixed, verified rewe.de destinations and the domain allowlist used by the REWE ordering assistant, see "REWE-Bestellassistent" below).
  - **Store / persistence** (~446) — the entire data model and its `localStorage` I/O. See "Data model" below.
  - **Demo data** (~521) — `seedDemoData()` / `removeDemoData()`, all demo records are tagged `isDemo:true` so they can be identified and bulk-removed.
  - **Toast & Modal** (~578) — `toast()`, `openModal()`/`closeModal()`, rendering into the static `#toast-root` / `#modal-root` containers.
  - **Router** (~593) — hash-based routing (`#/path` or `#/path/param`), see "Routing & rendering" below.
  - **Theme** (~662) — applies `data-theme` attribute to `<html>` per the stored setting.
  - **Derived data helpers** (~670) — cross-cutting queries over the store (e.g. `shoppingsInRange`, `avgPurchaseIntervalDays`, `avgPrice`) used by the dashboard and statistics views.
  - **Small UI builders** (~704) — shared render helpers used across views, e.g. `catChip`, `catIconEl`, `marketSelectOptions`, and (added for the REWE assistant) `marketAddressLines()`, `isReweMarket()`, `reweOrderStatusBadge()`.
  - **Per-view sections** (Dashboard ~743, Einkaufsliste ~836, Scan ~1103, Historie ~1201, Statistik ~1269, Produkte ~1442, Kategorien ~1511, Märkte ~1533, Suche ~1570, Einstellungen ~1596) — each contains a `viewX()` function returning an HTML string, plus any view-local state and chart-drawing functions (`svgLine`, `svgSparkline`, `drawStatistikCharts`, etc. — hand-written inline SVG, no charting library). The Einkaufsliste section also holds the voice-input state/parser/modal (see "Voice input" below) and the REWE order-wizard state/step-renderers (`reweOrderDraft`, `reweWizardHtml()` ~1003, see "REWE-Bestellassistent" below); Historie (~1201) additionally renders the `reweOrders[]` history card.

  - **Boot** (~2633) — `loadStore()`, `applyTheme()`, `window.addEventListener('hashchange', render)`, initial `render()`, and the first-run demo-data onboarding modal.

### Rendering model

There is no framework/virtual DOM. `render()` (in Router) reads `location.hash`, calls the matching `viewX()` function to get an HTML string, and does `view.innerHTML = html`. Every state change is followed by `saveStore()` (persist) and `render()` (re-render the whole current view from scratch) — there is no partial/diffed update, so **any action that mutates `store` must call both**, or the UI will silently drift from persisted state.

Interactivity is wired via inline `onclick="App.methodName('id')"` attributes generated inside the template strings, not event delegation. Because of this:
- Inline handler arguments must only ever be IDs/enum values (never raw user-entered text) — anything else can break the HTML attribute on names containing quotes.
- All interpolated user-facing text (product names, notes, market names, etc.) must go through `esc()` (for HTML content) or `escAttr()` (for `value="..."` attributes) — this is how the app avoids XSS/markup breakage from a product named e.g. `Chips & "Salz"`.
- A few continuous-input fields (the receipt-scan review table) intentionally skip a full `render()` on every keystroke to avoid losing focus/cursor position — they mutate the in-memory draft object directly and patch just the total via a targeted DOM update (`updateScanTotalDisplay()`). Follow this pattern for any other free-text field inside a list/table if a full re-render would steal focus.

### Data model (`store`, `STORAGE_KEY = 'wochenkorb.store.v1'`)

Single JSON blob in `localStorage`, shape defined by `freshStore()`:

```
{ version, categories[], products[], shoppingList[], shoppings[], priceHistory[], markets[], reweOrders[], categoryCorrections{}, settings{} }
```

- `products[]` — the catalog (name, categoryId, barcode, defaults, `favorite`, `purchaseCount`, `lastPurchasedAt`, `isDemo`, plus the optional REWE-matching fields `reweProductId`/`reweProductName`/`reweProductUrl`/`reweLastMatchedAt` — see "REWE-Bestellassistent" below).
- `shoppingList[]` — the *current, active* list (unchecked + checked-but-not-yet-completed items), each referencing a `productId`. All add-to-list entry points (typed quick-add, chip taps, voice input) funnel through the same `addItemCore(productId, quantity?, unit?)` (~1666) — the two trailing params are optional overrides for the product's own defaults, added for voice input (see "Voice input" below) without changing behavior for the existing call sites that omit them.
- `shoppings[]` — completed purchase history. Each `Shopping` embeds its own denormalized `items[]` (name/qty/price/categoryId snapshotted at purchase time) — **not** a live reference to `products[]`. This is intentional: deleting a product must not corrupt past history (see `deleteProduct()` vs. how `viewVerlaufDetail` renders items straight from the embedded snapshot).
- `priceHistory[]` — one entry per (product, shopping) purchase, used for price-trend charts and market price comparison; rebuilt/appended whenever a shopping is saved (`completePurchase`, `confirmScan`).
- `markets[]` — besides `name`, optionally carries `street`/`zip`/`city` and `reweStoreId` (the real REWE market identifier, left `null` unless the user enters one themselves — see "REWE-Bestellassistent" below).
- `reweOrders[]` — REWE order records prepared by the ordering assistant; each embeds its own denormalized `items[]` snapshot (same "don't corrupt history if the source changes" reasoning as `shoppings[]`), not a live reference to `shoppingList[]`/`products[]`. See "REWE-Bestellassistent" below.
- `categoryCorrections{}` — a `normalizedProductName → categoryId` map. `classifyProduct()` checks this before falling back to `CATEGORY_KEYWORDS` substring matching; it's how the app "learns" from manual category corrections during receipt review.
- Deleting a category reassigns any referencing `products`/`shoppingList` items to the `Sonstiges` category (`sonstigeId()`) rather than leaving dangling references — replicate this pattern for any new entity-deletion logic.

### Receipt scanning

`Kassenzettel scannen` uses a real `<input type="file" accept="image/*" capture="environment">` (opens the phone camera on mobile) followed by canvas-based downscaling/compression (`compressImage()`, max width 1000px, JPEG q=0.72) before the image is stored inline as a data URL on the `Shopping` record.

OCR is real, via **Tesseract.js**, run entirely client-side (`runRealScan()`, ~2091) — no image is ever sent anywhere. Because this project has no build step/bundler, the library itself is **lazy-loaded from a CDN** (`loadTesseract()`, ~2077) only when a scan starts, not at page load. This has one important consequence documented in "Deploy" above: **the Claude Artifact viewer's strict CSP blocks external script/network requests**, so `loadTesseract()` will fail there (and on any fully offline device) — this is caught deliberately and surfaces as the normal `scanState.status='error'` UI with a "Manuell erfassen" fallback, rather than crashing. On GitHub Pages / `npx serve` / `file://` it works normally, downloading the German (`deu`) language model on first use (cached by the browser afterward). `Tesseract.recognize()` is called with `tessedit_pageseg_mode: '6'` ("assume a single uniform block of text") rather than the default automatic layout detection — this is more reliable for the narrow, columnar text on a photographed receipt. When touching this code, verify **both** paths: a real scan on GitHub Pages/`npx serve`, and the graceful-failure message inside a Claude Artifact (or with dev tools offline).

`parseReceiptText()` (~2117) turns Tesseract's raw recognized text into structured items with a line-based heuristic (not a general receipt parser) — this was tuned against a real photographed Kaufland receipt (not just clean synthetic text), which surfaced most of the edge cases below:
- **Market/date/total**: known market names are matched in the first few lines; a `dd.mm.yyyy`-style date anywhere in the text; a "Summe/Gesamt/Total" line (not "Zwischensumme") for the printed total.
- **Item cutoff**: only lines *before* the Summe line are considered for items — everything after (payment method, tax-rate breakdown table, Kundenbeleg footer) is guaranteed not to be a product and is ignored outright, rather than relying on `RECEIPT_NOISE` to catch every possible footer line. Since OCR sometimes garbles "Summe" itself beyond recognition (seen in testing: read as "Sunne"), there's a second, independent cutoff anchor — the payment-method line (`kartenzahlung|ec-cash|girocard`) — and whichever anchor appears first in the text wins.
- **Price extraction** (`findTrailingPrice()`, ~2162, inside `parseReceiptText`): takes the *last* valid `\d{1,4}[.,]\d{2}` number found anywhere in the line, not a strict end-of-line anchor. Real photographed receipts frequently have OCR noise/watermark artifacts trailing the actual price (e.g. a line reads as `2,79 B VA A` or `1.748 U 8` instead of `2,79 B`) — an end-anchored regex threw such lines away entirely; this cost 12 of 20 real items in testing before the fix.
- **Quantity**: recognizes both a leading `Nx` prefix (`2x Produkt`) and the "menge × Einzelpreis" format printed inline by some tills (`Produkt  2 * 0,79  1,58`, i.e. quantity/unit-price embedded before the line-total price) — the latter is stripped out of the name so it doesn't end up as name junk.
- **Negative amounts are never imported as items** — a leading `-` on the trailing price (Rabatt, Pfand-Rückgabe, Storno, e.g. `Leergut Getränke -12,02`) causes the line to be skipped. `Pfand`-labelled lines are also skipped via `RECEIPT_NOISE` regardless of sign (deposits aren't products).
- **`excludedAdjustment`**: Pfand and negative amounts are excluded from the item list, but they *are* part of the printed Summe. `parseReceiptText()` tracks their net effect in `draft.excludedAdjustment` (Pfand adds, negative amounts subtract) so `viewScanReview()` can compare the sum of imported items against `total - excludedAdjustment` instead of `total` directly — otherwise the "Preise prüfen" mismatch warning would fire on essentially every receipt that has any Pfand or discount line, even when everything was recognized correctly.

It's intentionally forgiving rather than exact — the review table is always editable before saving, since OCR/parsing mistakes are expected on real photos (a garbled price with no recoverable decimal separator, e.g. a comma OCR'd away entirely, still can't be recovered and has to be added manually).

Each parsed item is matched against the existing catalog by `normName()`; unmatched names are flagged `isNew:true` and shown with a "Neu" badge in the review table purely as a UI hint. The actual auto-creation of new products happens where it already did before this OCR change — `findOrCreateProduct()` (~509), called from `confirmScan()` for every item, creates a catalog entry if none matches by normalized name. This is generic to scanned, manually-typed, *and* voice-parsed items alike (see "Voice input" below) and needs no special-casing per input source.

If the OCR engine is ever swapped again, keep it behind the same `scanState` contract (`idle → scanning → review → (confirm/cancel)` or `error`) so the rest of the flow (review/edit table, category auto-classification, `confirmScan()`) keeps working unchanged.

### Voice input (Spracheingabe)

The mic button next to the `#add-input` field on the Einkaufsliste view (`viewListe()`, ~860) lets the user add items by speaking, e.g. "Füge 2 Liter Milch, 1 Packung Butter und 6 Eier hinzu". It uses the browser-native **Web Speech API** (`SpeechRecognition`/`webkitSpeechRecognition`, `lang:'de-DE'`) rather than a bundled library — no CDN load, no CSP exposure beyond what the browser's own mic-permission dialog already requires, consistent with the zero-dependency constraint.

State lives in `voiceState` (`{status:'idle'|'listening'}`), `voiceRecognition`, `voiceDraft`, `voiceRawText` — all module-level `let`s declared alongside `listAddQuery` at the top of the Einkaufsliste section, mirroring the `scanState` pattern used for receipt scanning:
- `startVoiceInput()` (~1729, in Actions) feature-detects the API, creates a `SpeechRecognition` instance lazily (only on first mic click, never at page load), and wires `onresult`/`onerror`/`onend`. Clicking the mic again while `status==='listening'` calls `.stop()` instead of starting a second recognition (toggle behavior).
- **Errors are mapped to German toasts**, not left to crash or hang: `not-allowed`/`service-not-allowed` (mic permission denied), `no-speech`, `audio-capture` (no mic found), `network`; `aborted` (user-initiated stop) is deliberately silent — no toast, just a state reset — since that's the expected outcome of the toggle-to-stop action, not a failure. Missing browser support is checked upfront and shows a toast on click rather than crashing or hiding the button.
- A recognized transcript goes through `parseVoiceCommand()` (~1694) — a heuristic NLU parser in the same spirit as `parseReceiptText()` (tuned against the example phrases in the feature request, not a general-purpose grammar): strips known German lead-in phrases ("Füge … hinzu", "Ich brauche", "Setze … auf die Liste", etc.) via `VOICE_LEAD_RE`/`VOICE_TAIL_RE`, splits on commas/"und"/"sowie", then per segment extracts a leading quantity (digit or a small set of German number words in `VOICE_NUMBER_WORDS`) and a unit token (`VOICE_UNIT_WORDS`, mapped onto the existing `UNITS` list) before treating the remainder as the product name.
- Parsed items are **never added directly** — they populate `voiceDraft` and open a confirmation modal (`voiceDraftModalHtml()`, ~983, reusing the standard `openModal()`/`.modal-head` styling) showing the raw recognized text plus one editable row per item (quantity/unit/name, each removable). This mirrors the receipt-scan review step's philosophy: speech recognition and heuristic parsing are expected to be imperfect, so nothing is committed to `store` until the user confirms. Per-keystroke edits in the modal (`updateVoiceDraftItem()`) intentionally mutate `voiceDraft` **without** re-rendering the modal, for the same reason the scan-review table skips per-keystroke `render()` — see "Rendering model" above; only structural changes (removing a row) re-render it.
- `confirmVoiceItems()` (~1794) resolves each draft item against the catalog the same way `quickAddByName()` does (`normName()` match, else `findOrCreateProduct()` + `classifyProduct()`), then calls `addItemCore(productId, quantity, unit)`.

Because `SpeechRecognition` requires live microphone access, it fails the same way inside the Claude Artifact viewer's sandbox as Tesseract.js does (see "Receipt scanning" above and "Deploy" at the top) — this is caught by the normal `onerror` path and surfaces as a toast, not a crash. When touching this code, verify on GitHub Pages/`npx serve` with mic access actually granted, *and* that a denied/unsupported mic still leaves the app fully usable (mic button resets, rest of the list UI untouched).

### REWE-Bestellassistent (REWE ordering)

The "🛒 Bei REWE bestellen" button on the Einkaufsliste view (`viewListe()`, ~860; disabled when there are no unchecked items) opens a 3-step modal wizard that turns the current open list items into a REWE order draft and then hands the user off to `rewe.de` — it does **not** place an order through any REWE API.

**Why a hand-off and not a real integration**: REWE has no public order/cart API for third-party apps (confirmed by research at implementation time; only unofficial scraper services exist, which were deliberately not used). Given the zero-backend constraint, the only technically honest option is to prepare the list and redirect the user to REWE's own site to finish there themselves. The UI and code must never claim the order was placed — only "vorbereitet" (prepared) or "an REWE übergeben/weitergeleitet" (handed off/redirected), matching the `reweOrders[]` status values below.

**Wizard state and flow** — module-level `reweOrderDraft` (`{step, marketId, orderId, items[]}`), declared alongside `voiceState` at the top of the Einkaufsliste section, mirrors the `scanState`/`voiceDraft` in-memory-draft pattern: nothing touches `shoppingList[]` until the user confirms.
- `openReweOrderWizard()` (~1843, Actions) snapshots the currently open (`!checked`) list items into `reweOrderDraft.items` (each with its own editable `quantity`/`unit`/`included`) and opens the modal at `reweWizardHtml()` (~1003, Einkaufsliste section), which dispatches on `step` to one of `reweWizardMarketStepHtml()` / `reweWizardItemsStepHtml()` / `reweWizardSummaryStepHtml()`.
- **Step 1 (Markt)**: lists `store.markets` (REWE-named ones sorted first via `isReweMarket()`), reuses the existing market management (`openMarketModal(id, prefillName)` — extended with a `prefillName` param so "➕ REWE-Markt hinzufügen" can prefill "REWE") rather than duplicating a market form. If the selected market has no `reweStoreId`, a banner explains this and offers to edit the market or continue anyway — the wizard **never fabricates** a `reweStoreId`, it only reads whatever the user already entered.
- **Step 2 (Artikel)**: per item, quantity/unit are edited in place without a full `render()` (same reasoning as the scan-review table and voice draft, see "Rendering model" above — only `toggleReweDraftItemIncluded()` triggers a re-render since it's a structural change). Items with no `reweProductName`/`reweProductUrl`/`reweProductId` on the underlying product show "⚠️ Kein eindeutiges REWE-Produkt gefunden" and a "Produkt auswählen" button — there is no automated REWE product search (none exists publicly), so this opens the ordinary product-edit modal (`openProductModal()`) for the user to paste in what they found themselves on REWE's site.
- **Step 3 (Übersicht)**: on first reaching this step, a `reweOrders[]` record is created with `status:'prepared'` (see below); "An REWE übergeben" attempts the actual hand-off.
- **Resuming across modal switches**: because "Markt bearbeiten"/"REWE-Markt hinzufügen"/"Produkt auswählen" each open a *different* modal (replacing the wizard's `#modal-root` content), `saveMarketForm()` (~2455) and `saveProductForm()` (~2355) both end with `closeModalOrResumeRewe()` instead of a plain `closeModal()` — if `reweOrderDraft` is still active, the wizard reopens at its current step afterward instead of the user simply landing back on the Einkaufsliste view. This is a deliberate, narrowly-scoped exception to the "one modal at a time" default; don't extend the same reflex to unrelated modals (editItem, completePurchase, etc.) without the same "was this reachable mid-wizard" reasoning.

**Product/market model additions** (all optional, all `null` unless the user fills them in — see "Data model" above): `markets[].street`/`zip`/`city`/`reweStoreId`, `products[].reweProductId`/`reweProductName`/`reweProductUrl`/`reweLastMatchedAt`. Saving a product (`saveProductForm()`) rejects a non-empty `reweProductUrl` that doesn't pass `isAllowedReweUrl()` with a toast, rather than silently storing an arbitrary link.

**External URL safety** (`isAllowedReweUrl()`/`openReweUrl()`, ~1811): every outbound REWE URL — the two hardcoded constants `REWE_SHOP_URL`/`REWE_MARKET_SEARCH_URL` *and* any user-entered `reweProductUrl` — is validated against `REWE_ALLOWED_HOSTS` (`rewe.de`/`www.rewe.de`/`shop.rewe.de`, HTTPS only) before `window.open()` is ever called. URLs are never interpolated directly into an `onclick`/`href`; buttons only ever call an ID-based handler (`App.openReweProductLink('${productId}')`) that looks the URL up and validates it at call time. `openReweUrl()` also checks `navigator.onLine` and catches a blocked/failed `window.open()`, surfacing the exact German error messages this feature requires ("Prüfe deine Internetverbindung…", "Du kannst REWE auch manuell öffnen.") instead of throwing.
- `attemptReweRedirect(record)` (~1834) is the single place that flips a record from `prepared`/`redirected` to `redirected` on a successful `window.open()`; both `reweWizardSubmit()` (~1916, from the wizard) and `reweRetryOpen()` (~1928, from Historie, for retrying later without reopening the wizard) call it — don't duplicate this logic.
- **Not verified inside an actual Claude Artifact**: like the Tesseract CDN load and `SpeechRecognition`, a `window.open()` popup may be blocked or sandboxed by the Artifact viewer's CSP. `openReweUrl()`'s try/catch means this degrades to the same German error toast rather than a crash, but if this is ever tested for real inside an Artifact and found to fail silently, that's the first place to look.

**`reweOrders[]` records** (created by `reweWizardGoToSummary()`, ~1889 in Actions): `{id, marketId, marketName, createdAt, status, redirectedAt, completedAt, cancelledAt, items[]}`, where each item embeds the product's REWE fields *as they were at prepare-time* (same denormalization reasoning as `shoppings[].items`). `status` moves `prepared → redirected` automatically (via `attemptReweRedirect`) and `→ cancelled` if the user cancels from the summary step; it only reaches `completed` through an explicit, user-initiated "Als abgeschlossen markieren" click in Historie (`reweMarkOrderCompleted()`, ~1934) — the app itself can never know whether an external REWE order actually completed, so it must never set this status on its own. The Historie view (`viewVerlauf()`, ~1201) renders a "REWE-Bestellungen" card above the regular purchase list, using `reweOrderStatusBadge()` for the status label — kept visually and structurally distinct from `shoppings[]` entries (a REWE hand-off is not the same thing as a completed local purchase).

### App icon (favicon / apple-touch-icon / web manifest)

The app icon (a hand-authored neon shopping-basket SVG, TRON-styled to match the rest of the UI) is embedded directly in the `<link>`/`<meta>` tags at the top of the file (lines ~6–13) as **data URIs** — there is no separate `.svg`/`.png` asset file, keeping the single-file constraint intact:
- `<link rel="icon" type="image/svg+xml">` — the crisp SVG favicon for modern browsers.
- `<link rel="icon" type="image/png" sizes="32x32">` — small PNG fallback favicon.
- `<link rel="apple-touch-icon" sizes="180x180">` — shown when added to the home screen on iOS.
- `<link rel="manifest">` — an inlined (data-URI) web manifest with 192×192 and 512×512 icons, for "Add to Home Screen"/install on Android.
- `<meta name="theme-color">` and the `apple-mobile-web-app-*` meta tags, for a cleaner standalone-launch appearance.

The 180/192/512px icons are stored as **JPEG, not PNG** — the icon's background is fully opaque (no transparency needed), and JPEG compresses its glow/gradient far better than PNG (a PNG export of the same icon was ~5–10× larger). This keeps the total embedded-icon footprint to ~80 KB despite four different sizes. All of this is data URIs, so — unlike Tesseract.js — it works identically under the Claude Artifact viewer's strict CSP (no external request is made).

There's no build step to regenerate these: if the icon is ever redesigned, re-render the SVG to a `<canvas>` at each target size (`canvas.toDataURL('image/jpeg', 0.92)` for the raster sizes, keep the 32px favicon as PNG since it's tiny) and paste the resulting data URIs back into the `<link>`/manifest tags by hand.

### File download/export

`Export (JSON)`/`Export Historie (CSV)` both go through `offerDownload()` (~2529), which branches on whether a Claude runtime is present — this is the **only** place in the app that touches `window.claude`, and the only *deliberate* functional difference between the two deployment channels:
- **Inside the Claude Artifact viewer** (`window.claude.use` exists): uses the `downloads` runtime capability (`window.claude.use('downloads')`). A plain `<a download>` link is inert inside that sandbox, so this path is required there; it also handles `extension_not_enabled` (retries the CSV export as `.txt`) and a user `declined` response.
- **Everywhere else** (GitHub Pages, `file://`, `npx serve`, ...): falls back to `nativeDownload()` (~2518), a standard `Blob` + temporary `<a download>` click — ordinary browser download, no Claude dependency at all.

Both paths must keep working — when touching export/import, verify with `window.claude` both present (mock `window.claude.use` in the console) and absent (plain `npx serve`, the GitHub Pages case). Import (`importJson()`) has no such split — it's a plain `<input type="file">` + `FileReader`, which already works identically everywhere.

### CSS design system

All theming is CSS custom properties on `:root`, following a **dark-first** three-state pattern (the app currently ships a TRON-inspired dark HUD aesthetic as the default):
- Bare `:root` defines the dark palette (the default/system look).
- `@media (prefers-color-scheme: light)` + `:root:not([data-theme="dark"])` overrides to a light "glass" companion palette.
- `:root[data-theme="light"]` repeats the light overrides so the in-app theme toggle (Einstellungen → Hell/Dunkel/System) wins regardless of OS preference.

Effects like glow/bloom are tokenized (`--glow-sm`, `--glow-md`, `--text-glow`, `--chart-glow`) rather than hardcoded per component, specifically so the light theme can disable/soften them (a static neon text-shadow looks wrong on a white background) — when adding a new glowing element, use the tokens rather than a literal `rgba(0,229,255,...)` shadow. Category/series colors (`--cat-1`…`--cat-8`) are picked per-category via a stable hash (`catColorVar()`), not by list position, so a given category keeps the same color across renders and datasets.
