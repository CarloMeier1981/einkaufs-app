# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**Wochenkorb** is a German-language, mobile-first grocery shopping list web app: shopping list, receipt scanning (mocked OCR), purchase history, spending statistics, product/category/market management. All data is stored client-side in `localStorage` — there is no backend and no build step.

The entire application — HTML shell, CSS design system, and all JavaScript — lives in the single file `index.html` (~2000 lines). This is deliberate: the same file is also published as a self-contained Claude Artifact, which does not support external JS/CSS files, `import` modules, or a build step. Any change must keep working as one file.

## Commands

There is no `package.json`, no build tool, no linter, and no automated test suite — this is intentional for a zero-dependency single-file app.

- **Run locally**: serve the directory with any static file server, e.g. `npx serve .`, then open the printed URL. Opening `index.html` directly via `file://` also works but is not representative of how it's deployed (Artifact / GitHub Pages), so prefer a real HTTP server when testing.
- **Testing**: manual, in a browser. There is no unit/e2e test runner. When verifying a change, actually load the page and click through the affected flow (the app has no error boundary beyond the try/catch in `render()`, which only prevents a white screen — it does not validate correctness).
- **Deploy**: the file is pushed as-is to `https://github.com/CarloMeier1981/einkaufs-app` (`main` branch) and/or republished as a Claude Artifact. There is no CI/build pipeline in between — whatever is in `index.html` on `main` is the shipped app.

## Architecture

### File layout inside `index.html`

- Lines 1–3: `<title>` and the single external dependency — a Google Fonts `<link>` (Orbitron + Titillium Web). No other external resources are loaded; the app must keep working fully offline after first load.
- Lines 4–301: `<style>` — the entire CSS design system (see below).
- Lines ~302–316: the static app shell markup (`#app`, `.sidebar`, `.topbar`, `#view`, `.bottomnav`, `#modal-root`, `#toast-root`). This is the *only* HTML that isn't generated by JS — everything inside `#view`, `#modal-root`, `.sidebar` and `.bottomnav` is rendered at runtime.
- Lines 317–1998: one `<script>` block, organized into clearly delimited sections (search for `/* ===== Section Name ===== */`):
  - **Utilities** (~319) — `esc`/`escAttr` (HTML-escaping for interpolated user text), `fmtEUR`, `fmtDate`, `normName` (diacritic-stripping normalizer used for search/matching), date-range helpers.
  - **Constants** (~335) — `DEFAULT_CATEGORIES`, `DEFAULT_MARKETS`, `UNITS`, `CATEGORY_KEYWORDS` (keyword → category auto-classification map), `DEMO_PRODUCT_POOL` (used both for demo-data seeding and the mock receipt scanner).
  - **Store / persistence** (~398) — the entire data model and its `localStorage` I/O. See "Data model" below.
  - **Demo data** (~471) — `seedDemoData()` / `removeDemoData()`, all demo records are tagged `isDemo:true` so they can be identified and bulk-removed.
  - **Toast & Modal** (~528) — `toast()`, `openModal()`/`closeModal()`, rendering into the static `#toast-root` / `#modal-root` containers.
  - **Router** (~543) — hash-based routing (`#/path` or `#/path/param`), see "Routing & rendering" below.
  - **Theme** (~612) — applies `data-theme` attribute to `<html>` per the stored setting.
  - **Derived data helpers** (~620) — cross-cutting queries over the store (e.g. `shoppingsInRange`, `avgPurchaseIntervalDays`, `avgPrice`) used by the dashboard and statistics views.
  - **Per-view sections** (Dashboard ~678, Einkaufsliste ~771, Scan ~907, Historie ~1002, Statistik ~1053, Produkte ~1226, Kategorien ~1295, Märkte ~1317, Suche ~1354, Einstellungen ~1380) — each contains a `viewX()` function returning an HTML string, plus any view-local state and chart-drawing functions (`svgLine`, `svgSparkline`, `drawStatistikCharts`, etc. — hand-written inline SVG, no charting library).
  - **Actions** (~1432) — every state-mutating function (add/edit/delete for products/categories/markets/list items, scan confirmation, import/export, etc.), ending in the `App = {...}` object (~1981) that re-exports them for use as `onclick="App.xxx(...)"` handlers.
  - **Boot** (~1992) — `loadStore()`, `applyTheme()`, `window.addEventListener('hashchange', render)`, initial `render()`, and the first-run demo-data onboarding modal.

### Rendering model

There is no framework/virtual DOM. `render()` (in Router) reads `location.hash`, calls the matching `viewX()` function to get an HTML string, and does `view.innerHTML = html`. Every state change is followed by `saveStore()` (persist) and `render()` (re-render the whole current view from scratch) — there is no partial/diffed update, so **any action that mutates `store` must call both**, or the UI will silently drift from persisted state.

Interactivity is wired via inline `onclick="App.methodName('id')"` attributes generated inside the template strings, not event delegation. Because of this:
- Inline handler arguments must only ever be IDs/enum values (never raw user-entered text) — anything else can break the HTML attribute on names containing quotes.
- All interpolated user-facing text (product names, notes, market names, etc.) must go through `esc()` (for HTML content) or `escAttr()` (for `value="..."` attributes) — this is how the app avoids XSS/markup breakage from a product named e.g. `Chips & "Salz"`.
- A few continuous-input fields (the receipt-scan review table) intentionally skip a full `render()` on every keystroke to avoid losing focus/cursor position — they mutate the in-memory draft object directly and patch just the total via a targeted DOM update (`updateScanTotalDisplay()`). Follow this pattern for any other free-text field inside a list/table if a full re-render would steal focus.

### Data model (`store`, `STORAGE_KEY = 'wochenkorb.store.v1'`)

Single JSON blob in `localStorage`, shape defined by `freshStore()`:

```
{ version, categories[], products[], shoppingList[], shoppings[], priceHistory[], markets[], categoryCorrections{}, settings{} }
```

- `products[]` — the catalog (name, categoryId, barcode, defaults, `favorite`, `purchaseCount`, `lastPurchasedAt`, `isDemo`).
- `shoppingList[]` — the *current, active* list (unchecked + checked-but-not-yet-completed items), each referencing a `productId`.
- `shoppings[]` — completed purchase history. Each `Shopping` embeds its own denormalized `items[]` (name/qty/price/categoryId snapshotted at purchase time) — **not** a live reference to `products[]`. This is intentional: deleting a product must not corrupt past history (see `deleteProduct()` vs. how `viewVerlaufDetail` renders items straight from the embedded snapshot).
- `priceHistory[]` — one entry per (product, shopping) purchase, used for price-trend charts and market price comparison; rebuilt/appended whenever a shopping is saved (`completePurchase`, `confirmScan`).
- `categoryCorrections{}` — a `normalizedProductName → categoryId` map. `classifyProduct()` checks this before falling back to `CATEGORY_KEYWORDS` substring matching; it's how the app "learns" from manual category corrections during receipt review.
- Deleting a category reassigns any referencing `products`/`shoppingList` items to the `Sonstiges` category (`sonstigeId()`) rather than leaving dangling references — replicate this pattern for any new entity-deletion logic.

### Receipt scanning

`Kassenzettel scannen` uses a real `<input type="file" accept="image/*" capture="environment">` (opens the phone camera on mobile) followed by canvas-based downscaling/compression (`compressImage()`, max width 1000px, JPEG q=0.72) before the image is stored inline as a data URL on the `Shopping` record. OCR itself is a clearly-labeled **mock** (`runMockScan()` / `mockGenerateReceipt()`) that fabricates plausible line items from `DEMO_PRODUCT_POOL` after a simulated delay, with a small random chance of simulating a "couldn't read receipt" failure — there is no real OCR/AI integration. If one is added, it should replace `runMockScan()`/`mockGenerateReceipt()` behind the same `scanState` contract (`idle → scanning → review → (confirm/cancel)` or `error`) so the rest of the flow (review/edit table, category auto-classification, `confirmScan()`) keeps working unchanged.

### File download/export

`Export (JSON)`/`Export Historie (CSV)` go through the Claude Artifact `downloads` runtime capability (`window.claude.use('downloads')`), not a plain `<a download>` — this only works when the page is viewed as a published Artifact with that capability declared. `offerDownload()` handles the case where `window.claude` doesn't exist (plain static hosting / GitHub Pages) by showing a toast instead of failing silently, and has a fallback for `extension_not_enabled` (retries the CSV export as `.txt`). Keep this graceful-degradation path if touching export code, since the app is deployed both as an Artifact and as a plain static site.

### CSS design system

All theming is CSS custom properties on `:root`, following a **dark-first** three-state pattern (the app currently ships a TRON-inspired dark HUD aesthetic as the default):
- Bare `:root` defines the dark palette (the default/system look).
- `@media (prefers-color-scheme: light)` + `:root:not([data-theme="dark"])` overrides to a light "glass" companion palette.
- `:root[data-theme="light"]` repeats the light overrides so the in-app theme toggle (Einstellungen → Hell/Dunkel/System) wins regardless of OS preference.

Effects like glow/bloom are tokenized (`--glow-sm`, `--glow-md`, `--text-glow`, `--chart-glow`) rather than hardcoded per component, specifically so the light theme can disable/soften them (a static neon text-shadow looks wrong on a white background) — when adding a new glowing element, use the tokens rather than a literal `rgba(0,229,255,...)` shadow. Category/series colors (`--cat-1`…`--cat-8`) are picked per-category via a stable hash (`catColorVar()`), not by list position, so a given category keeps the same color across renders and datasets.
